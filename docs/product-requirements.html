1. Product purpose and desired outcome

1.1 Problem

Photos, stories, personal expressions, music, and tributes to Roy can otherwise remain scattered across family devices, messages, social networks, and external services. A new visitor may encounter the circumstances of his death without understanding the person, his relationships, or the life he lived. Family members also need control over which public contributions appear.

1.2 Product

A Hebrew-first, right-to-left, responsive memorial website dedicated to רועי משה. Its primary public experience is a single scrolling narrative, supported by interactive content and a moderated memory-submission flow. A separate password-protected administration page lets the family review visitor contributions.

1.3 Desired outcomes

  • Help visitors understand Roy as a person before reading about the circumstances of his death.
  • Preserve approved personal stories, photographs, language, places, music, and acts of remembrance in one accessible destination.
  • Allow friends, relatives, and others to contribute memories without creating accounts.
  • Give the family explicit control over publication, rejection, and deletion of contributions.
  • Make the website maintainable by a developer who did not build the original implementation.
  • Preserve dignity, factual accuracy, and family privacy.

The emotional narrative is: meet Roy → understand his personality → explore his life and relationships → read what happened → see how his memory continues. This is a personal memorial, not an institutional obituary template or a product centered only on tragedy.

1.4 Success criteria

Current analytics baselines and numeric targets have not been established. The initial definition of success is behavioral:

OutcomeEvidence / proposed measurement
Visitors can learn about RoyMain content and navigation work on mobile and desktop; owner approves factual and visual presentation.
Contributions are safely moderatedNo pending or rejected memory appears in the public API or public cards.
Family can operate the siteAn authorized person can sign in, review, approve, reject, and delete a submission.
Site remains usable when external services failMemorial text remains available; music fallback link and map error presentation are usable.
Site is maintainableA new developer can run, build, change approved content, regenerate API clients, and understand publishing prerequisites.

Future measurement could include aggregate visits, successful submissions, submission errors, moderation turnaround, and availability. Tracking design, consent implications, and numeric targets require owner approval; custom event instrumentation is not documented as implemented.

1.5 Scope and non-goals

In scope now: Hebrew public memorial, curated content, image galleries and carousels, interactive places map, Spotify player, YouTube tribute, visitor memory submissions, server-side moderation, persistent database and sessions, production publishing.

Not implemented / not current scope: Visitor accounts, public discussion threads, likes, donations, payments, commerce, mobile native app, multilingual content, administrator CMS for all sections, runtime photo uploads, automated approval, AI-authored biographies, email notifications, multi-admin roles, MFA, bulk moderation, and full moderation audit history.

1.6 Alternatives and product rationale

Shared folders preserve photos but do not provide a coherent public story or moderation. Social networks provide reach but distribute content across feeds and platform accounts. Generic memorial templates can provide a page but may not reflect Roy’s personality or the requested interactions. These are functional alternatives, not conclusions from a formal competitor study.

  • /admin is the administration page, intentionally absent from public navigation.

  • /api/* is routed to the backend, not the frontend SPA.
  • Fixed navigation links target #about, #timeline, #memories, #gallery, #places, #music, #october7, and #tributes.

3.5 Gallery and shared lightbox

The gallery uses responsive masonry-style columns and lazy-loaded curated images. Selecting a photograph opens an enlarged dialog that shows the entire photograph using object-contain, rather than permanently cropping it.

Current shared lightbox behavior:

  • Close using its close control or Escape.
  • Move with visible controls, keyboard arrows, or mobile swipes.
  • RTL keyboard mapping: left arrow advances; right arrow goes backward.
  • Mobile swipe threshold is 50 pixels.
  • Enlarged lightbox navigation stops at the first and last photo; it does not wrap.
  • Lock background scrolling, trap focus within the dialog, and restore focus to the opener.

The preview carousel and enlarged lightbox deliberately have different end behavior: carousel arrows wrap; lightbox arrows clamp.

3.6 Places map and privacy

Approved places appear as cards and markers. Only entries with numeric coordinates are mapped. Selecting a card or marker synchronizes the active place and focuses the map. Re-selecting a place can focus it again.

  • Leaflet / React Leaflet render OpenStreetMap tiles and required attribution.
  • Initial map zoom is 12; selection focuses the relevant place at zoom 14.
  • Mouse-wheel zoom is disabled to avoid hijacking page scrolling.
  • The map mounts when near the viewport, using an IntersectionObserver margin of 300 pixels.
  • Desktop uses a side list; smaller screens use a horizontal list and scroll the map into view after selection.
  • Mapping failures must not remove the entire memorial page; the map has an error boundary.
  • Current configured places include the family-home pin and a Beersheba fire-station location.

Standing privacy requirement: The family-home pin is approved, but its written street address and house number must remain hidden. Do not introduce the address into text, popups, captions, accessibility labels, or external links. This handoff intentionally omits the exact location. Frontend map coordinates are still technically inspectable; approval of a visible pin is not equivalent to hiding the point from a technically capable visitor.

4. Visitor memory-submission requirements

4.1 User journey

  1. Visitor reaches Memories and selects “שתפו זיכרון משלכם”.
  2. A responsive dialog opens with the form; no account or page navigation is required.
  3. Visitor supplies their name, relationship, a writing prompt, memory text, optional email, and consent.
  4. The browser validates the form; the server independently validates it.
  5. On successful insertion, the visitor sees a thank-you / pending-review state.
  6. The submitted memory does not appear publicly until an administrator approves it.
  7. There is no email receipt, public status tracker, contributor editing, or draft autosave.

4.2 Input contract

Blank optional email is normalized away. The backend owns status, IDs, and timestamps; visitors cannot choose approved status. Client validation is for usability, not a security boundary.

4.4 Public list behavior and failure states

  • Query returns only approved memories, newest submission first.
  • Display author, relationship, selected prompt, and memory text; preserve line breaks.
  • Loading shows skeleton cards; failure and empty state are explicit.
  • Empty state explains that memories appear after family approval.
  • Refetch every 30 seconds; approval elsewhere is therefore not instant push delivery.
  • Disable repeated submission while the request is pending.
  • On failure, retain input and show a Hebrew error notification.
  • Do not optimistically publish a newly submitted memory.

4.5 Abuse limits

Submission is limited to five requests per 15 minutes per IP in the current rate-limit store. JSON bodies are capped at 16 KB. Populated honeypots are rejected. These reduce simple abuse but are not a CAPTCHA, distributed spam defense, or duplicate-submission guarantee.

5. Administration and moderation

5.1 Access model

Administration uses one shared password verified by bcrypt on the server, plus a PostgreSQL-backed session. It does not use public user accounts, Clerk, Replit SSO, JWT storage in the browser, or client-only password checks.

To operate the published site:

  1. Open https://roy-moshe-memorial.replit.app/admin.
  2. Enter the administrator password configured by the owner.
  3. Review the default pending tab ממתין לאישור.
  4. Approve with the approval action or reject with the rejection action.
  5. Use deletion only when permanent removal is intended.
  6. Sign out when finished, particularly on shared devices.

Never request or share the administrator password in chat, this document, logs, or source control.

5.2 Review interface

The signed-in administrator sees tabs and counts for pending, approved, and rejected submissions. Private cards include the author, relationship, optional email, prompt, text, status, and submission date/time. Dates use the browser’s local timezone.

  • Approve is available for non-approved records.
  • Reject is available for non-rejected records.
  • Delete is available with confirmation.
  • API supports returning a record to pending, but the current UI does not expose that action.
  • No text editing, search, bulk operations, pagination, per-reviewer identity, or administrator notifications.
  • Successful actions invalidate private and public queries in the same browser; other visitors update through their normal polling.
  • Logout clears the private client cache.

5.3 State-transition logic

ActionNew statusPublic?Timestamp logic
Visitor submitspendingNoServer creates createdAt and updatedAt; no review time.
Admin approvesapprovedYesUpdate updatedAt; set reviewedAt to now.
Admin rejectsrejectedNoUpdate updatedAt; set reviewedAt to now.
Admin resets through APIpendingNoUpdate updatedAt; clear reviewedAt.
Admin deletesRecord removedNoHard deletion, not a status or soft-delete flag.

Approved records can be rejected later; rejected records can be approved later. Re-review overwrites the review timestamp rather than preserving a history. Public ordering is based on submission time, not approval time.

Deletion consequence: The application has no undo or restoration interface. A database backup recovery process, if available, is separate and has not been verified here.

5.4 Login and session rules

  • Login limited to five attempts per 15 minutes per IP.
  • Invalid credentials return 401; missing configuration returns 503.
  • Valid login regenerates the session to reduce session-fixation risk.
  • Session cookie: roy.admin, HTTP-only, SameSite Strict, secure mode auto, path /api/admin, four-hour maximum age.
  • Sessions persist in admin_sessions, not process memory.
  • The session table must already exist; runtime session setup does not create it automatically.
  • Admin responses use Cache-Control: no-store.
  • Cross-site mutation requests are rejected using Origin and Fetch Metadata checks.
  • Logout destroys the session and clears the cookie.

Shared credentials do not identify which family member performed an action. MFA, role separation, account recovery, and auditable reviewer identity are future design decisions, not existing capabilities.

6.4 Frontend implementation details

The application wraps routes in QueryClient, tooltip, toast, and error-boundary providers. Query defaults include one retry and no refetch on window focus. Wouter respects the configured artifact base path. Public section anchors and backend requests must remain compatible with artifact routing; avoid hardcoded localhost URLs in browser code.

The theme uses Heebo, warm off-white backgrounds, warm dark text, and a muted terracotta primary color. Content is mobile-first Hebrew RTL. Decorative cutouts use an isolated visual lane so faces do not overlap copy or controls.

Standing visual scope: Hero, gallery, October 7, and the closing section intentionally omit large cutout backgrounds. Preserve that decision rather than applying decoration uniformly. Motion in decorative cutouts responds to reduced-motion preferences; broader motion behavior still needs review.

401Invalid password or missing authenticated administrator session.

404Requested moderation record does not exist.

Password input is restricted to 1–200 characters by the contract. Moderation IDs must be positive safe integers. Express trusts one proxy hop; cookie and IP behavior depend on correct deployment routing.

Gap: OpenAPI primarily documents successful responses. Error schemas and status responses should be added before treating generated clients as a complete error contract.

8.3 Content-storage boundaries

9. Security, privacy, and content governance

9.1 Required invariants

  • Public reads filter approved status on the server.
  • Admin authorization is enforced on the server for every private endpoint.
  • Passwords are not stored as plaintext; only a bcrypt hash is configured.
  • No fallback administrator credential or fallback session secret.
  • Client-submitted status and server-owned timestamps cannot grant publication.
  • Email is excluded from public response schemas.
  • Session cookies are not accessible to JavaScript.
  • Secrets stay out of code, documentation, screenshots, and logs.
  • Personal facts and images require family approval.
  • Home written-address privacy applies to visible text and nonvisual labels.
  • Memory text is treated as text, not trusted HTML.

9.2 Current limitations

  • Rate-limit counters are process-local by default. Autoscale instances can have independent counters; a distributed store would be required for a consistent site-wide limit.
  • Origin checks are a current protection, not proof that every possible CSRF or proxy configuration has been audited.
  • Shared administrator password has no per-person accountability.
  • No immutable moderation audit trail.
  • Consent is stored as a boolean, without an explicit policy version or separate consent timestamp.
  • Retention periods, privacy-policy wording, deletion-request process, and backup recovery commitments have not been formally specified.
  • Third-party font, tile, video, and music requests may transmit visitor network/device information to those providers. YouTube’s privacy-enhanced domain does not mean “no third-party data processing.”

Before adding analytics, uploads, or more personal data, approve the privacy implications with the owner. This handoff does not make a legal-compliance claim.

10. Accessibility, responsiveness, and quality requirements

10.1 Desired baseline

Use WCAG 2.2 AA as the intended accessibility target, not as a current certification. Visitors should be able to navigate, read, submit, and browse images with touch, keyboard, and assistive technology.

Requirements:

  • Hebrew document language and RTL direction.
  • Meaningful heading hierarchy and descriptive controls.
  • Form labels, validation feedback, visible focus, and modal focus management.
  • Keyboard-operable cards, accordions, carousel controls, and lightbox.
  • Sufficient contrast and comfortable mobile tap targets.
  • Browser text zoom must remain possible.
  • Essential content must not depend solely on animation, color, hover, or the map.
  • Respect reduced-motion preferences across the whole experience.
  • Never place decorative photos over text or controls.

10.2 Known accessibility gaps

The current viewport metadata includes maximum-scale=1, which can impede zoom. The mobile navigation toggle has an English accessible label. Reduced-motion handling is present for decorative cutouts but has not been established consistently for smooth scrolling and all entrance effects. Fix and verify these rather than claiming the site is fully accessible.

10.3 Performance and resilience

Current techniques include optimized WebP media, lazy image loading, viewport-deferred map/player mounting, error boundaries, skeletons, and API error states. They are not measured performance results.

Acceptance goals:

  • Main biography remains readable if Spotify, YouTube, or tiles are unavailable.
  • An API failure does not remove unrelated static memorial content.
  • Image frames reserve useful space and remain responsive.
  • Large media are optimized before committing or publishing.
  • Build output and dependency warnings are reviewed, without hiding them as successful performance work.

Public and private memory lists currently fetch all matching records without pagination. This is adequate only while data volumes remain modest; reassess before growth creates slow queries or large responses.

10.4 SEO and sharing

Current document title and Hebrew language are configured. Description, Open Graph description, and Twitter description still contain placeholder content. Canonical URL and a complete social sharing image setup are not established in the reviewed HTML.

Required completion: owner-approved metadata, production canonical URL, approved share image, and inspection of the actual shared preview. The app is a client-rendered SPA; do not assume every crawler renders all content. A sitemap, crawl policy, or prerendering approach should be evaluated if search discoverability becomes a priority.

11.5 Database change policy

Generate and review migrations; keep them checked in. Apply production schema changes through the supported Replit publishing migration flow. Do not execute startup DDL, automatically seed development fixtures in production, or treat development push-force as a production release method.

Before changes, confirm environment and whether the change can destroy data. Backups, recovery ownership, and restoration drills should be agreed with the owner rather than assumed.

11.6 Content-change workflow

  1. Receive owner-approved text or assets.
  2. Update typed content / the relevant component only where necessary.
  3. Preserve exact approved Hebrew, dates, and photo ordering.
  4. Optimize new images and supply appropriate alternative text.
  5. Check RTL, mobile layout, lightbox behavior, privacy, and placeholders.
  6. Type-check/build the coherent set of changes.
  7. Verify the changed public view and any changed critical data flow.
  8. Publish through the owner-approved publishing process.

There is no generic content-management UI. Changing biographies or adding tribute photos currently requires a source change and new build.

15. Glossary

  • Curated content: Family-approved material maintained in code/configuration, not visitor submissions.
  • Pending: Submitted but not publicly visible.
  • Approved: Visible through the public memory API.
  • Rejected: Retained privately but not visible publicly.
  • SPA: Single-page application; client routing handles public and admin views.
  • SSR: Server-side rendering; not the current primary frontend delivery model.
  • ORM: Database access layer; Drizzle is used here.
  • OpenAPI: Shared machine-readable API specification used to generate client and validation code.
  • Session: Server-stored login state referenced by a protected browser cookie.
  • Artifact: A registered workspace application/service with its own routing/build metadata.
